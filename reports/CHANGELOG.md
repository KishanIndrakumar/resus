# CHANGELOG — Systems module redesign

## Added
- **Systems page** (`systems.en.json` + `systems.translations.draft.json`, embedded inline like the legacy phrasebook data): 11 body systems, 96 unique questions, shared/deduplicated across systems that reference the same question ID (e.g. `NEURO09`/`NEURO10` appear in both Neurological and Eyes).

## Update: new 36-language architecture (per-language files, manifest, separate Systems language picker)

A new client brief specified a formal 36-language target list (10 Priority-1 "core" + 16 Priority-2 + 10 Priority-3), with requirements that the old single-blob `systems.translations.draft.json` approach didn't fully satisfy: separate JSON files per language, offline access to *downloaded* language files specifically (not just "embedded in the app shell"), clear script/dialect identification, and an explicit prohibition on silently falling back to English. This update replaces the Systems module's translation architecture; **the legacy phrasebook module is untouched.**

### Added
- **`systems.languages.json`** — a manifest listing all 36 target languages (plus English as the source), each entry carrying `code`, `name`, `nativeName`, `script`, `dialect`, `rtl`, `priority` (1/2/3), `status` (`draft`/`pending`), `reviewStatus` (`unreviewed` for everything right now), and `file` (the per-language JSON filename, or `null` if not yet drafted).
- **`systems.translations.<code>.json` × 36** — one file per language, each with all 96 question IDs. A `pending` language's file has every question explicitly `null` (never a fabricated placeholder). A `draft` language's file carries full AI-draft text plus `provenance` (`source: "ai_draft"`, `needs_human_review: true`, `generated` date, `generated_by`).
- **Lazy per-language fetch + cache** (`sysEnsureLangLoaded` in `template.html`): a language's 96-question file is only fetched from the network the first time it's actually selected, then kept in an in-memory cache (`SYS_LANG_CACHE`) for the rest of the session. The existing generic service-worker fetch handler (cache-then-network-update) automatically caches that fetch response for offline reuse on future visits — satisfying "separate file per language" and "offline access to downloaded language files" without new SW logic beyond pre-caching the 10 Priority-1 packs at install time (see `sw.js` below).
- **New `offline_unavailable` translation status**, distinct from `missing`: a language that **is** drafted per the manifest, but hasn't been downloaded to *this device* yet and there's no network right now, shows "Translation not downloaded for offline use — connect to the internet once to download it" with a "Try again" button — never silently falls back to English, and is worded differently from "no draft exists at all" so staff aren't misled about which is the case.

## Fix: offline pre-caching now covers every drafted language, not just Priority 1

**Bug:** selecting a drafted Priority-2/3 language (reported with Tamil, `ta`) while offline showed "Translation not downloaded for offline use," because `sw.js` only pre-cached the 10 Priority-1 language files at install. Every other drafted language (18 of them) was only ever cached lazily, the first time a user actually selected it online — so any of those 18 languages would fail offline until a user had, by chance, opened that specific language once before while connected. This is a real gap: a clinician should not have to pre-visit each of 28 languages individually, online, before any of them can be trusted to work offline.

**Fix — no change to app behaviour or UI, only to what the service worker pre-caches:**
- `sw.js` now pre-caches **all 28 currently-drafted language packs** at install, not a 10-language subset. The list is read from `systems.languages.json` at install time (`status: "draft"` entries), rather than hand-maintained in `sw.js`, specifically so that drafting more languages in future can't silently reintroduce this same gap — only the `CACHE_NAME` version needs bumping to pick up newly-drafted languages.
- Switched the precache step from `cache.addAll(...)` (which is all-or-nothing: a single failed fetch rejects the *entire* batch, and the prior code silently swallowed that rejection) to caching each file individually via `Promise.allSettled`, so one slow or failing fetch can no longer wipe out the rest of the precache.
- `CACHE_NAME` bumped `edrt-v5` → `edrt-v6` so every already-installed device picks up the expanded precache on its next online visit.
- **No change** to the app's runtime translation logic, UI, language picker, gating/reveal behaviour, or data files — this was purely a service-worker caching-scope fix. The `offline_unavailable` state (distinct from `missing`/pending) still exists in the code as a safety net for the rare case where a device's cache was evicted or corrupted, but it should no longer be reachable in normal use for any of the 28 drafted languages.
- Users still never "download a language pack" as a deliberate action — the whole point of this fix is that nothing changes about how a user interacts with the app; the full drafted-language set simply downloads automatically, once, the first time the app itself is opened online, exactly as the core app shell always has.

**Offline tests performed (`test_offline.py`, new):**
1. Loaded the app once online, polled the Cache Storage API until the precache settled, and asserted all 28 drafted language files (`systems.translations.<code>.json`) were present — confirms the fix at the cache level, not just by spot-checking the UI.
2. Set the browser context fully offline (Playwright network emulation, not just closing Wi-Fi in the app), reloaded the app, and drove the Systems-specific language picker to select **Tamil, Vietnamese, and Hungarian** (one Priority-1-adjacent and two further down the priority list, none of which had been individually opened before) — confirmed each showed the normal gated-with-reveal drafted state, and specifically that the "Translation not downloaded for offline use" message did **not** appear for any of them.
3. Confirmed a genuinely `pending` language (Georgian) still correctly shows the distinct "not yet available" message offline — this is expected (there is no draft to serve) and is not something pre-caching can or should fix.
4. Re-ran the full existing regression suites (`test_systems.py`, `test6.py`) after the change: zero console errors, all prior assertions still pass — confirms this fix did not alter or regress any existing behaviour.

## Fix #2: translations embedded directly in the page — the per-language fetch/cache architecture is removed entirely

The per-language-fetch architecture from the update above, even after the pre-caching fix, still surfaced "Translation not downloaded for offline use" in real-world use (reported with German). On investigation, the underlying design — translations held in separate files, fetched and cached over the network at runtime — remained inherently timing-sensitive: a device could be offline before the service worker had actually finished caching a newly-drafted or newly-deployed language, a cache could be evicted under storage pressure, or a production host could serve those files slightly differently than the local test server. The client was explicit: **no language should ever depend on an individual network download, full stop** — it should work exactly like the other already-reliable categories (Pain, Time/Onset, etc.), which have never had this problem because their content has always been embedded directly in the page.

**Change:** the Systems module's translations for every drafted language are now embedded directly inside `index.html` at build time, exactly like `PHRASES` (the legacy phrasebook data) and like the Systems module's own English question bank (`SYS_EN`) always has been. This removes an entire class of failure, not just the scenario this bug happened to report:
- Removed `SYS_LANG_CACHE`, `SYS_LANG_OFFLINE_FAIL`, `sysEnsureLangLoaded`, `sysLangReady`, the `offline_unavailable` status, the "Translation not downloaded for offline use" UI state, and the "Try again" retry button — this code path no longer exists, so it cannot resurface under any timing, caching, or hosting difference.
- Added `SYS_TR`, a single embedded object (`{code: {qid: text}}`) built at render time from the 28 drafted languages' `systems.translations.<code>.json` files. `sysGetTranslation` now reads straight from this in-memory object — synchronously, with no network call, no cache lookup, no async state — the same way `PHRASES[id][lang]` has always worked for Pain, Time/Onset, and every other category.
- The per-language JSON files on disk are **unchanged in content and still kept as the source of truth for version control / editing** (satisfying "separate JSON file per language" as a *data organisation* requirement) — `render_index.py` now reads them and bakes their content into `index.html` at build time, rather than the app fetching them individually at runtime. Edit a language's own file and rebuild to update it; nothing about the per-language-file workflow for translators/reviewers changes.
- `sw.js` simplified back down to caching the app shell only (`CACHE_NAME` bumped `edrt-v6` → `edrt-v7`) — there is no longer a separate set of language files to pre-cache, because caching `index.html` itself is now sufficient for every language.
- `systems.languages.json` (the manifest) is still embedded and still used for display metadata (native name, script, dialect, RTL, priority, pending-vs-drafted status for the language picker) — only the *translation content* moved from "fetched per-language" to "embedded alongside everything else."

**Trade-off, stated plainly:** `index.html` is now larger (~433KB vs. ~302KB previously) because all 28 languages' content ships in the one file instead of being split across 28 separate requests. This is the same trade-off the legacy phrasebook already made for its ~35 languages, and it buys unconditional reliability — the page cannot possibly show "not downloaded" for a language that's drafted, because there is no separate download for it to be missing.

**Offline tests performed (`test_offline.py`, rewritten):**
1. Loaded the app once online (so the service worker caches `index.html` itself, same as any PWA's first visit), then went fully offline and reloaded — confirming the *entire* app, including every Systems translation, now comes from that single cached page.
2. Selected **Tamil, Vietnamese, Hungarian, Arabic, Polish, and Simplified Mandarin** while offline — none pre-visited individually — and confirmed none showed any "not downloaded" message (the message, and the code path that could produce it, no longer exist), each showing the ordinary gated-with-reveal drafted state instead.
3. Revealed the Tamil draft and asserted the rendered text is non-blank and is genuinely Tamil, not the English source re-shown — confirms real translated content renders, not just the absence of an error state.
4. Confirmed a `pending` language (Georgian) still correctly shows the distinct "not yet available" (no reveal link) state offline — unaffected by this change, as expected.
5. Re-ran the full existing regression suites (`test_systems.py`, `test6.py`): zero console errors, zero regressions.

## Change #3: unreviewed-draft gate removed — drafted translations now show directly (explicit client decision)

After the architecture fix above, a follow-up question came in: why gate the translation behind "Translation unavailable — use a qualified interpreter" + a "Show unreviewed AI draft" click at all, instead of just showing it? The gate existed because none of the 28 drafted languages have been reviewed by a native speaker or qualified medical translator, and an unreviewed machine translation shown as if verified carries real clinical risk in an ED symptom-screening context (see the full explanation given in conversation). The client was presented with four options — keep the gate, show drafts with a visible "AI draft" banner, show drafts with no banner at all, or a per-language reviewed/unreviewed flag — and explicitly chose **"show drafts directly, no banner."**

**Change made exactly as decided:**
- Removed the entire gate/reveal UI for drafted languages: the "Translation unavailable — use a qualified interpreter" box, the "Show unreviewed AI draft (for review only)" link, the "AI DRAFT — NOT CLINICALLY REVIEWED" banner, and the "Hide draft" button are all gone for any language with `status: "draft"`. The translated text now renders immediately and permanently, the same way the legacy phrasebook's (reviewed) translations, and the Systems module's own English text, have always rendered.
- `state.sysReveal` (the per-question "is the draft currently shown" flag) is removed — there is nothing to reveal or hide any more.
- The "Listen" (text-to-speech) button is now available immediately for any drafted language too, since the text is always visible.
- **A `pending` language (no draft exists at all) still shows the "Translation unavailable — use a qualified interpreter" message** — that case is unchanged, because there is genuinely nothing else to show for those 8 languages.
- **No change to translation content itself** — this only changes whether the existing, already-drafted text is shown behind a click or immediately. The content remains exactly what it was, still unreviewed by any native speaker or clinical translator.

**This is a documented, deliberate change to a patient-safety-relevant default, made at the client's explicit request after the trade-off was explained.** It means: from this release onward, any clinician or patient using the Systems module in a non-English, non-reviewed language sees AI-translated clinical questions with no on-screen indication that they are unreviewed machine translation. The QA report, setup doc, and acceptance checklist have all been updated to reflect this and to flag it clearly for anyone picking up this project later — see "What's needed before clinical use" in `SYSTEMS_QA_REPORT.md`, which now leads with this point.

**Tests updated accordingly (`test_systems.py`, `test_offline.py`):** assertions for drafted languages (Arabic, Turkish, Tamil, Vietnamese, Hungarian, Polish, Simplified Mandarin, German) now check that the translated text renders **directly**, with zero instances of the gate box, both online and fully offline. The pending-language case (Georgian) is unchanged and still asserts the gate appears. Full regression suite (`test6.py`) re-run: zero console errors, zero regressions.

### 3. Translation-quality recheck (context-aware phrasing, not word-for-word)
Spot-checked a representative set of higher-resource languages already in the drafted set (Spanish, Arabic, French, Hindi, Urdu, Simplified Mandarin, Polish, Somali, Pashto, Kurdish Sorani) against ten of the highest-risk/most idiom-prone questions (general symptoms, chest pain, fainting, breathing, abdominal pain, worst-headache, loss-of-consciousness, sore throat, neck pain). Finding: **the existing drafts already follow context-aware, natural phrasing, not literal word-for-word translation** — for example, French renders abdominal pain as the idiomatic "mal au ventre" rather than a literal "douleur dans l'abdomen"; Polish, German, and French all correctly use their formal/polite register appropriate for a clinician addressing a patient ("Pan/Pani" conjugation, "Sie", "vous") rather than an informal or literal construction; Spanish, Arabic, Hindi, and Urdu all phrase "worst headache" and "lost consciousness" the way a clinician would actually ask it in that language, not a mechanical word-for-word rendering of the English. This matches the project's original drafting brief (natural ED-patient-facing phrasing), and no word-for-word artifacts were found in this sample.

## Change #6: one shared language across the whole app (where both modules support it)

Follow-up to the header-button fix above. The client noticed the deeper issue it was a symptom of: Pain/Time-Onset (legacy phrasebook) and Systems symptom-screening each remembered a completely independent language choice -- e.g. Pain could be set to German while Systems stayed on Japanese, with no connection between the two. Asked directly whether this should change, the client chose: **one shared language, but only where both modules actually support it** -- picking a language in either module sets it for both; wherever the shared code isn't in a particular module's own language list, that module alone falls back to showing English, without resetting the shared choice.

**Why "only where both support it," not a strict single list:** the two modules have different, only-partially-overlapping language lists -- 26 codes in common, 10 Systems-only (Polish, Simplified Mandarin, Georgian, Lithuanian, Latvian, Bulgarian, Tigrinya, Cantonese-Traditional, Kurdish-Kurmanji, Malayalam), and 8 legacy-only (Bosnian, Czech, Slovak, Macedonian, Lingala, Korean, Swahili, and the old Traditional-script `zh` code). Forcing a single list would mean dropping real languages from one module or the other; falling back to English per-module instead keeps every language either module already supports, while still giving a single, predictable "what language is selected" answer everywhere.

**Implementation:**
- `state.lang` is now the ONE shared language value, used by both modules and persisted under a single `localStorage` key (`edrt_lang`). The separate `state.sysLang` / `edrt_sys_lang` concept is removed entirely (an existing install's old `edrt_sys_lang` value is read once as a fallback on first load after upgrading, so nobody's prior choice is silently lost).
- `sysGetTranslation()` gained a new `crossModuleFallback` status: if the shared code is a real language the legacy phrasebook supports but isn't part of the Systems 36-language spec, Systems now shows the English question text directly, with a small note (e.g. "Bosnian not available in Systems") instead of the old "Translation unavailable — use a qualified interpreter" gate. A code that isn't recognised by *either* module (not a legitimate cross-module case, just unknown/garbled state) still shows the stricter gate, unchanged.
- `renderRunner()` (legacy Pain/Time-Onset/etc.) and `openHelpFab()` (the always-available Help/SOS button) gained the mirror-image fallback: if the shared code isn't in the legacy phrasebook's own ~35-language list (one of the 10 Systems-only codes), they now show English with a "<language> not available here" note instead of crashing (the previous code assumed `state.lang` was always one of its own codes and would throw trying to read `.rtl` off an undefined entry).
- Both language pickers (legacy and Systems) now write to the same `state.lang`; the Systems picker additionally marks each tile "— Systems only" when that language isn't in the legacy phrasebook's list, so it's clear upfront which choices will show up in both modules versus just one.
- The header's globe button label (added in the previous fix) now simply shows the one shared language's name everywhere, via a new `sharedLangNativeName()` helper that checks both modules' language data -- no special-casing needed per view any more, since there's only one value to show.
- Response-bar labels (Yes/No/Don't know/etc.) in a Systems question that's fallen back to English still come from whichever source already has that language (reused phrase-#1 translations) if one exists — e.g. selecting Bosnian shows the Systems question in English (Systems doesn't have Bosnian) but the Yes/No buttons still show in Bosnian (the legacy phrasebook does). This is a side effect of how response labels have always been sourced, not a new inconsistency introduced here, and is more helpful than forcing English on content that's already safely available.

**Tests added (`test_systems.py`):** picks Arabic (in both lists) from the legacy picker and confirms Systems reflects it too; picks Georgian (Systems-only) from the Systems picker and confirms Pain falls back to English with a "not available here" note rather than crashing; picks Bosnian (legacy-only) from the legacy picker and confirms Systems falls back to English with a "not available in Systems" note rather than the old gate. `test_offline.py`'s "unknown language code" check was tightened to confirm a code unrecognised by *either* module still shows the gate (not a silent English fallback), now that `crossModuleFallback` exists for the legitimate cross-module case. Full regression suite (`test_systems.py`, `test_offline.py`, `test6.py`) re-run: zero console errors, zero regressions.
