# Setup / deployment + remaining issues

## Deployment
Static hosting only, no build step required beyond the one already in use:
1. Files to deploy together: `index.html`, `manifest.json`, `sw.js`, `icons/` (6 PNGs). That's it for what the app actually serves at runtime — every drafted Systems language's translations are embedded directly inside `index.html` (exactly like the legacy phrasebook's data, and like Pain/Time-Onset/every other category), so there is no separate `systems.translations.<code>.json` file to deploy or fetch at runtime any more. Those per-language files (plus `systems.languages.json` and `systems.en.json`) are still kept in the **build folder** as the source-of-truth/editable content, but they don't need to be uploaded to the live host — `render_index.py` bakes their content into `index.html` ahead of deployment.
2. GitHub Pages: push the folder as-is to the `gh-pages` branch (or `/docs`), or serve from any static host / `resus.ie` directly. All asset paths are relative (`./icons/...`, `./manifest.json`), so it works at a domain root or a subpath equally.
3. To change any Systems translation content: edit the relevant `systems.translations.<code>.json` file (or `systems.languages.json` to change a language's status/metadata) in the build folder, then run `python3 render_index.py` to rebuild `index.html`, then redeploy. Unlike the previous release, a translation-only change **does** require a rebuild now — this is the trade-off for removing the network-dependent fetch/cache path entirely (see CHANGELOG "translations embedded directly in the page" entry).
4. Any change to `template.html`'s structure, or any rebuild of `index.html` (including a translation content change), should bump `CACHE_NAME` in `sw.js` so already-installed devices fetch the new page on their next online visit rather than keep serving a stale cached copy. Bumped for this release: `edrt-v7` → `edrt-v8` (the remaining 8 languages were drafted and the "record date/time" button was redesigned — see CHANGELOG "Change #4").

## Technical: Systems-module translation architecture (updated — embedded, not fetched)
- **Translations for every drafted language are embedded directly inside `index.html` at build time** (`SYS_TR`, built by `render_index.py` from the per-language `systems.translations.<code>.json` files), exactly like the legacy phrasebook's `PHRASES` data. There is no runtime network fetch for translation content at all, and therefore no "language pack download," no per-language cache, and no "not downloaded for offline use" state — that entire code path (`SYS_LANG_CACHE`, `sysEnsureLangLoaded`, `sysLangReady`, `offline_unavailable`) has been removed, not just patched. This was an explicit client requirement after a per-language-fetch design (even once pre-caching every language, see the superseded entries below) still proved unreliable in practice: translations now behave identically to every other already-working category (Pain, Time/Onset, etc.), which have always worked this way.
- The per-language JSON files are still the editable source of truth for translation content and version control — only *how the app consumes them at runtime* changed (embedded at build time instead of fetched at runtime), not the file-per-language data organisation itself.
- `systems.languages.json` (the manifest) is still embedded separately and still drives the language picker's metadata (native name, script, dialect, RTL, priority, `draft` vs `pending` status) — only translation *content* moved out of the fetch-at-runtime model.
- The prior 34-language batch's content was **reused**, not retranslated, for every language that overlaps the 36-language spec (28 of 36). Two Priority-1 languages (Polish, Simplified Mandarin) were freshly translated, and the remaining 8 languages (Georgian, Lithuanian, Latvian, Bulgarian, Tigrinya, Cantonese-Traditional, Kurdish-Kurmanji, Malayalam) have since been drafted too — **all 36/36 target languages now have a full 96-question draft, 0 pending.**
- Seven languages from the old 34-language batch (`bs, cs, sk, mk, ln, ko`, and the old Traditional-script `zh` code) are **outside** the 36-language spec. Their files still exist on disk but are deliberately excluded from `systems.languages.json`/`SYS_TR` and unreachable from the app's Systems language picker.
- **Language selection is now shared app-wide** (a single `state.lang`, one `edrt_lang` localStorage key) — picking a language in either the Systems module or the legacy phrasebook sets it for both, per explicit client decision (CHANGELOG "Change #6"). The two modules still have different, only-partially-overlapping language lists (26 codes shared, 10 Systems-only, 8 legacy-only), so wherever the shared code isn't in a given module's own list, that module alone falls back to showing English with a plain "<language> not available here/in Systems" note — it never crashes and never silently shows English with no explanation. The Systems picker still has its own layout (priority-tier grouping) separate from the legacy picker's flat grid, since the metadata differs, but both write to the same shared value.

## Remaining clinical issues
- **Systems module translations are 0% clinically reviewed, AND — as of an explicit client decision — this is no longer flagged to the user in the app.** All 36 of 36 languages now have a full AI draft (96/96 questions each). Previously, every non-English translation was gated behind "Translation unavailable — use a qualified interpreter" with an explicit "Show unreviewed AI draft" opt-in and a persistent "AI DRAFT — NOT CLINICALLY REVIEWED" banner. **That gate and banner have been removed at the client's request** (see CHANGELOG "unreviewed-draft gate removed") — drafted translations now display immediately. A small "AI translated" tag has since been added back next to the translated text (CHANGELOG "Change #5") as a lightweight visibility cue — but it is not a gate: it doesn't block, hide, or require a click, and it doesn't explain what "unreviewed" means. The underlying review status is completely unchanged: still 0% reviewed by a native speaker or qualified medical translator. Native-speaker review remains a materially more urgent next step than before the gate was removed — flag this explicitly to anyone picking up this project, and to clinical governance before any patient-facing use. **This now covers all 36 languages, not 28** — the review workload grew with the 8 newly-drafted languages.
- **All 8 previously-`pending` languages are now drafted** (`ka, lt, lv, bg, ti, yue-Hant, kmr, ml`) — there is no longer any language in the app with "no draft at all." A spot-check for natural/context-aware (not word-for-word) phrasing across a sample of languages found the existing drafting methodology already produces idiomatic, ED-patient-facing phrasing (see CHANGELOG "Change #4" for specific examples) — but this is a style spot-check, not clinical or linguistic review, and does not substitute for it.
- **Tigrinya and Kurdish-Kurmanji (the two newly-drafted languages I have least confidence in) should be prioritised early for native-speaker review**, alongside the already-flagged lower-resource languages (Kurdish Sorani, Pashto) — same reasoning: lower representation in the underlying model, so translation confidence is lowest there.
- **`NEURO11` / `TRAUMA05` / `CVS05` wording overlap** (see QA report) recurs across the drafted set, including the newly-completed languages, and still needs a clinical decision — ideally resolved once at the English-source level rather than patched per-language.
- **No clinical decision support, triage score, or diagnosis is implied anywhere** in the Systems summary by design — confirm this reads clearly to end users in practice, not just in the copy.

## Remaining linguistic issues
- **All 36 of 36 target languages now have draft Systems translations.** None have been checked by a native speaker; only by the automated duplicate/length checks in the QA report, plus a style spot-check (see CHANGELOG "Change #4") confirming natural/idiomatic phrasing in a sampled subset.
- Translation confidence varies by how well-represented each language is in the underlying model's training data. Higher-resource languages are likely more reliable drafts than lower-resource ones (Kurdish Sorani, Pashto, Tigrinya, Kurdish-Kurmanji, and similar outside the Priority-1 set). This is a draft-quality concern on top of the standing "nothing is clinically reviewed yet" caveat, and should inform review prioritisation — alongside the brief's own instruction to review the 10 Priority-1 languages first regardless of individual confidence level.

## Remaining copyright/licensing issues
- `systems.en.json`'s 96 questions are original content written for this project (not reproduced from the BRC/NHS phrasebook), so no licensing constraint carries over from that source for the Systems module specifically — unlike the legacy 62-phrase module, which remains attributed to the British Red Cross/NHS Emergency Multilingual Phrasebook.
- The Systems-module translations are AI-generated; if a future professional translation vendor is used for review/correction, confirm their contract terms for IP ownership of the corrected strings before merging them back in.

## Remaining security/governance issues
- Unchanged from the rest of the app: no backend, no account system, no analytics, no data transmission. The Systems module's session-only answer state was built to the same standard (never written to `localStorage`, IndexedDB, cookies, or any remote endpoint).
- The per-question "reveal unreviewed draft" control is a UI safeguard, not a technical access-control: anyone using the app can tap it. It is a nudge toward the safe default, not a permissions system. If a hard block is required (e.g. for a junior-staff or public-kiosk deployment), that would need a separate, actual mode/permission mechanism — flagged here as a gap in the current implementation, not solved.
